# MARGINALIA: Phase 04 "Audit & Ceremony" Plan

**Status:** Partly executed: everything that needs no outside party is done and tested, see `docs/phase4_audit_ceremony_report.md` (the external audits and the real ceremony are not done yet; the native O2 build is verified) · **Duration:** 6–10 weeks (mostly waiting for outside parties) · **Prerequisite:** Phase 03 complete and the code frozen (`v0.3.0-rc1`)
**Successor:** Phase 05 "Mainnet" (deposit cap, multisig guardian, a guarded launch)

## 1. Starting facts that shape the plan (checked in the repo)

| Fact | Impact |
|---|---|
| The current setup is a **development setup**: `scripts/build-circuit.sh` creates a **local** Powers of Tau and one Phase-2 contribution from one person. Whoever holds the "toxic waste" can forge proofs and drain the pool (risk L1 in `devbrief.md`) | Fine for testnet, **not allowed for mainnet**. The ceremony is an absolute mainnet requirement |
| The circuits are small: `withdraw.circom` 112 lines, `ragequit.circom` 49, `lib/merkle.circom` 37 | The circuit audit is narrow, cheap and freezable |
| Contracts to audit: `MarginaliaPool` 339 lines, `MagistrateRegister` 127. `Groth16Verifier` and `RagequitVerifier` are generated by `snarkjs` (it is enough to show they are identical to the final `zkey`, not to audit them line by line). `MarginaliaTokenPool` (312 lines, ERC-20) is **out of scope** unless it will be deployed | Lowers the audit cost |
| `scripts/ceremony-tool.js` only wraps `snarkjs` (contribute / verify / beacon / export); `test/ceremony.test.js` only checks the *verification key* export | Orchestration, transcripts, public verification and a clean rehearsal are needed |
| The tools were not installed on this machine: `circom`, `circomspect`, `slither`, `echidna`, `forge`, `halmos`, `solhint` | Install in CI/Docker in task A1 |
| Critical path: **circuit audit → fixes → circuit freeze → ceremony → redeploy the verifier**. A ceremony for circuits that are still changing is wasted | The order must not be reversed |

## 2. Architecture decisions

| # | Decision | Reason |
|---|---|---|
| D1 | Phase 1 uses the **public Powers of Tau (Hermez/PSE, `powersOfTau28_hez_final_15.ptau`)**, with the hash matched against published values | Trusted as long as 1 of dozens of contributors is honest; no need to run Phase 1 ourselves |
| D2 | Phase 2: a **coordinated sequential ceremony** (our own `snarkjs`-based tool, or p0tion if the infrastructure exists), at least **15 independent contributors**, then a **public random beacon (drand)** | Security needs only 1 honest contributor; the beacon closes the last-contributor gap |
| D3 | **Two separate zkeys** (withdraw, ragequit), one ceremony each | Two circuits, two verifiers |
| D4 | **Audit before the ceremony**; after the audit the circuits and contracts are frozen; changes afterwards trigger a new ceremony | Avoids double cost |
| D5 | The mainnet verifier = **the export of the final zkey**; tests confirm that the deployed verifier bytecode equals the export from the published final zkey | Closes the "verifier differs from the ceremony" gap |
| D6 | No new features during Phase 04 (only fixes of audit findings) | Keeps the freeze |

## 4. Schedule

| Week | Work | Gate |
|---|---|---|
| 1 | A0 + A1; send the pack to candidate auditors; recruit ceremony contributors | A-TEST1..4 green |
| 2–6 | B and C run in parallel (`E`); D-T1/T2/T3 done internally | Initial findings received |
| 6–8 | Fixes, re-test, the final report; **circuit freeze** | The auditor confirms no open Critical/High findings |

| 10 | E, hand over to Phase 05 | Every gate green |

Parallelism: B and C run together; D (tooling and rehearsal) can start before the freeze, but **the real ceremony only after the circuit freeze**.

## 5. Risks

| Risk | Mitigation |
|---|---|
| Auditor cost and queue | Book a slot from week 1; keep the scope narrow (without `MarginaliaTokenPool`, generated verifiers) |
| A Critical finding in the circuit after the ceremony is scheduled | The ceremony only after the freeze; D-T1..T3 done beforehand so only execution remains |
| Too few contributors or someone drops out | Recruit ≥ 20 for a target of 15; spare slots; the ceremony stays valid as long as ≥ 1 is honest, but the target of 15 is for public trust |
| Entropy leaks or a dishonest contributor | One honest contributor + the drand beacon is enough; an air-gapped guide; a public transcript |
| The on-chain verifier does not match the final zkey | D-TEST4 and D-TEST3 must be green before mainnet |
| The dev setup is accidentally still used | Test D-TEST6; the documents say clearly "dev setup = testnet only" and CI blocks a mainnet deploy with a dev verifier (`test/mainnet_guard.test.js` extended) |

## 6. Definition of done
1. Two audit reports (ZK and contract) are published, with no open Critical/High findings, and every finding has a regression test.
2. The Phase-2 ceremony is done (≥ 15 contributors + beacon), the transcript and the public verifier are available, and verified by independent parties.
3. The production verifier = the export of the final zkey (D-TEST4) and a dev proof is rejected (D-TEST6).
4. Every Phase 03 quality gate stays green on the final code.
5. The runbook, bug bounty and legal review are ready for Phase 05.

## 7. Decisions needed

4. **Whether `MarginaliaTokenPool` (ERC-20) is launched too**; if not, it stays out of the audit.
5. **The initial mainnet deposit cap** and the bug-bounty programme.
